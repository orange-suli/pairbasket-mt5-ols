# TMGM Pair US Index EA v7.0 修改方案备案

## 1. 文档目的

本文档记录对原版 `TMGM20260820PairUSIndex(1).mq5`（v6.1）的改造方案、实际落地内容、参数含义、状态机设计、风险控制和测试建议。

本次改造的核心目标有两个：

1. **极端偏离行情阶梯加仓**：首次触发极端 Z-Score 后，如果偏离继续扩大，则按固定 Z-Score 间距逐层增加同方向 Pair 仓位，改善 Basket 平均建仓位置。
2. **强制盈利后退出**：不再只因为 Z-Score 回到平仓阈值就立即平仓，而是先确认“回归已经发生”，再等待整组 Basket 净盈利达到指定阈值后统一退出。

同时，本次改造补充了多层仓位必须具备的状态管理、失败回滚、重启恢复和整组平仓逻辑。

---

## 2. 原策略保留部分

以下核心指标逻辑保持不变：

```text
ret1 = ln(Symbol1Price / Symbol1SMA)
ret2 = ln(Symbol2Price / Symbol2SMA)
logSpread = ret1 - ret2

Z = (logSpread - historicalMean) / historicalStd
```

保留：

- `GetPrices()` 的 `ln(P/SMA)` 偏离算法；
- `UpdateHistory()` 的历史序列维护方式；
- `CalculateZScore()` 的均值、标准差与 Z-Score 公式；
- 原有 LookBack、时间周期、冷却期、滑点和 Magic Number 机制；
- Symbol2 根据两边名义金额计算对冲手数的总体思路；
- `MODE_BOTH / MODE_ONLY_S1 / MODE_ONLY_S2` 三种交易模式。

本次重点修改交易管理，而不是重新设计统计指标。

---

## 3. 交易方向统一

### 3.1 原版问题

原版开仓只检查：

```text
Z >= ZScore_Open
```

而实际买卖方向由：

```text
logSpread > 0
```

决定。

这会产生“Z-Score 的方向”和“交易方向”不是同一个基准的问题。

### 3.2 v7.0 新规则

统一以 **Z-Score 的正负**定义 Pair 方向：

```text
Z >= +OpenZ
    → SHORT_SPREAD
    → Sell Symbol1 + Buy Symbol2

Z <= -OpenZ
    → LONG_SPREAD
    → Buy Symbol1 + Sell Symbol2
```

单腿模式也按照同一 Pair 方向映射到对应品种。

这样首仓、加仓、回归和平仓全部使用同一个统计尺度。

---

## 4. Basket 状态机

原版主要依赖“账户当前有没有 Position”判断交易阶段。多层加仓后，需要显式维护一个 Basket 状态。

新增核心状态：

```text
g_pairActive
    当前是否有活动 Basket

g_pairDirection
    SHORT_SPREAD / LONG_SPREAD

g_initialEntryZ
    首仓时 Z-Score

g_lastAddZ
    上一次实际成功加仓时的 Z-Score

g_addCount
    已成功加仓次数（不包括首仓）

g_lastAddTime
    上一次成功加仓时间

g_reversionReached
    当前 Basket 是否已经发生过回归

g_basketStartTime
    Basket 开始时间，用于统计本组佣金/费用和状态恢复
```

### Basket 生命周期

```text
无仓位
  ↓
|Z| 达到首仓阈值
  ↓
建立 Level 0
  ↓
创建 Basket 状态
  ↓
偏离继续扩大？ ──是──> 达到 AddZStep → Level 1/2/3...
  ↓
行情开始回归
  ↓
到达回归阈值
  ↓
ReversionReached = true
  ↓
Basket 净盈利达到 MinBasketProfit？
  ↓
整组退出
  ↓
确认所有腿全部关闭
  ↓
重置 Basket
  ↓
进入冷却期
```

## 5. 阶梯加仓设计

### 5.1 新增参数

```text
InpEnableScaleIn
    是否启用阶梯加仓

InpAddZStep
    两次实际加仓之间最少需要继续偏离多少 Z

InpMaxAddCount
    最大加仓次数，不含首仓

InpAddLotMultiplier
    Level N 手数 = 基础手数 × multiplier^N

InpMinAddIntervalSec
    两次加仓的最短时间间隔

InpMaxAbsZ
    |Z| 达到/超过该值后停止继续增加风险暴露

InpMaxTotalBaseLots
    基础腿最大总手数；0 表示禁用

InpMaxMarginUsagePct
    加仓前检查当前 Margin / Equity；0 表示禁用
```

### 5.2 加仓锚点

采用“上一次实际成功加仓的 Z”为下一层锚点，而不是固定绝对档位。

示例：

```text
首仓实际 Z = +2.08
AddZStep = 0.50

下一层条件：Z >= 2.58

若实际在 Z=2.62 成交：
LastAddZ = 2.62

下一层条件：Z >= 3.12
```

负方向镜像：

```text
首仓 Z = -2.08
下一层 = -2.58
再下一层 = 上一次实际成交Z - 0.50
```

### 5.3 一个 Tick 最多加一层

代码没有使用 `while()` 去补齐被价格跳空跨越的多个档位。

例如：

```text
LastAddZ = 2.50
AddZStep = 0.50

Z 从 2.60 突然跳到 3.80
```

本 Tick 只增加 **一层**，然后：

```text
LastAddZ = 3.80
```

下一层需等待新的 Z 间距。

目的：避免极端跳价时瞬间把全部允许仓位打满。

### 5.4 回归开始后停止加仓

只要 `g_reversionReached = true`，本 Basket 永远不再继续加仓。

即使后面再次波动，也按照“等待盈利退出”的状态管理，而不是重新逆势加仓。

---

## 6. 加仓手数

每一层基础手数：

```text
Level 0 = Lots
Level 1 = Lots × AddLotMultiplier
Level 2 = Lots × AddLotMultiplier²
Level 3 = Lots × AddLotMultiplier³
```

默认：

```text
AddLotMultiplier = 1.0
```

因此默认各层等手数，不使用马丁倍增。

在 `MODE_BOTH` 下：

1. 先根据 Level 计算 Symbol1 手数；
2. Symbol1 实际成交后；
3. 使用实际 Symbol1 成交量重新计算 Symbol2 对冲手数；
4. 再建立 Symbol2。

这样第一条腿发生部分成交时，第二条腿仍尽量按照实际第一腿名义金额配对。

---

## 7. Pair 开仓失败回滚

### 原版风险

原版在：

```text
Symbol1 开仓成功
Symbol2 开仓失败
```

时调用：

```text
CloseAllPositionsForSymbol(Symbol1)
```

单层策略下问题不大，但多层策略下会误把此前 Level 0/1/2 的 Symbol1 历史仓位一起关闭。

### v7.0 处理方式

每层订单使用：

```text
Pair_L0
Pair_L1
Pair_L2
...
```

作为 comment。

若本层第二条腿失败：

- Hedging 账户优先通过当前 Level comment 找到本次新增的独立 Position；
- Netting 账户只减少本次新增的对应 volume；
- 不调用“平掉这个品种全部仓位”；
- 已存在历史 Level 保持不变。

若第二条腿只发生部分成交，则本层两边都尝试回滚，避免新增一个失衡 Level。

---

## 8. 强制盈利退出

### 8.1 两阶段退出

正常退出由两道门组成。

#### 第一阶段：确认回归

SHORT_SPREAD：

```text
Z <= +ZScore_Close
```

LONG_SPREAD：

```text
Z >= -ZScore_Close
```

满足后：

```text
g_reversionReached = true
```

这个状态一旦成立，本 Basket 生命周期内不会取消。

#### 第二阶段：等待 Basket 净盈利

```text
GetBasketNetProfit() >= InpMinBasketProfit
```

才开始整组平仓。

因此：

```text
先回归、但仍亏损 → 继续持有
已经穿越均值、后来变为盈利 → 可以退出
```

不会因为 Z 离开极窄的回归区而失去平仓机会。

---

## 9. Basket 净盈利口径

`GetBasketNetProfit()` 包含：

### 当前未平持仓

```text
POSITION_PROFIT
+ POSITION_SWAP
```

### 本 Basket 开始以来的成交历史

加入：

```text
DEAL_COMMISSION
DEAL_FEE
```

如果 Basket 生命周期中产生过退出成交（例如本层失败回滚），还加入：

```text
DEAL_PROFIT
DEAL_SWAP
```

目的是让“盈利才平仓”尽量接近实际经济结果，而不是只看屏幕上的浮动 `POSITION_PROFIT`。

### 注意

最终成交后仍然可能因为：

- Bid/Ask 点差；
- 平仓瞬间滑点；
- 交易商最终佣金记账方式；

导致实现收益低于发单前判断值。

因此保留：

```text
InpMinBasketProfit
```

作为平仓成本缓冲，不建议长期设置为接近 0 的极小值。

---

## 10. 智能平仓重构

原版智能平仓每个品种通过 `GetPositionInfo()` 只读取一张 Position。

进入多层加仓后，这已经不能代表整个 Symbol1 或 Symbol2 的真实盈亏。

v7.0 改成：

```text
Symbol1 所有本EA持仓的 Profit + Swap 汇总
Symbol2 所有本EA持仓的 Profit + Swap 汇总
```

再决定先平哪一条腿。

### InpCloseProfitFirst = true

先平当前汇总盈利更高的一腿。

### InpCloseProfitFirst = false

先平当前汇总盈利更低的一腿。

每一条腿内部会循环关闭该品种所有 Level，并按照 `InpMaxRetries` 重试。

只有确认所有本 EA 管理持仓全部消失后，才允许：

```text
ResetBasketState()
StartCoolDown()
```

如果只平掉一部分，则：

- 不启动冷却；
- Basket 状态继续保留；
- 后续 Tick 继续管理剩余仓位。

---

## 11. 日内清仓规则

原版 GMT 指定小时，只要总浮盈大于 0 就可以日内清仓，未要求 Z 已经发生回归。

v7.0 默认：

```text
InpEndOfDayRequireReversion = true
```

因此默认日内清仓同样要求：

```text
ReversionReached = true
AND
BasketNetProfit >= MinBasketProfit
```

若未来希望“日内清仓是一套独立的风险规则”，可以把：

```text
InpEndOfDayRequireReversion = false
```

此时日内清仓可以不要求 Z 回归，但若 `InpRequireProfitClose=true`，仍然必须达到 Basket 最低盈利要求。

---

## 12. 重启状态恢复

多层策略不能只靠内存变量，否则 MT5 / EA 重启后会忘记：

- 当前方向；
- 加了几层；
- 上一次加仓 Z；
- 是否已经发生回归；
- Basket 开始时间。

v7.0 使用 **MT5 Terminal Global Variables** 保存：

```text
DIR
ENTRYZ
LASTZ
ADDC
ADDT
REVERT
START
```

冷却时间也单独持久化。

### 正常恢复

如果：

```text
账户有持仓
+ Global Variables 有Basket状态
```

则直接恢复原状态。

### 只有持仓但状态文件缺失

EA 会：

1. 根据当前 Symbol1/Symbol2 的实际方向推断 SHORT_SPREAD / LONG_SPREAD；
2. Hedging 账户尝试通过 Position 数量估算 Level 数量；
3. Netting 账户无法从 Position 数量准确反推历史加仓次数，因此安全地从 AddCount=0 开始；
4. 第一次重新取得有效 Z 后，只把当前 Z 当作新的 `LastAddZ` 锚点，不立刻补仓。

这优先避免“重启后误认为下一层早已满足，马上追加仓位”。

### 无法推断方向

如果账户持仓结构异常，例如两腿方向不构成标准 Pair，则自动加仓将无法正常继续。

此时日志会输出明确警告，应优先人工检查实际仓位。

---

## 13. 冷却期改造

原版多个平仓函数内部都会直接写：

```text
lastCloseTime = TimeCurrent()
inCoolDown = true
```

多层情况下可能出现：

```text
第一条腿已平
第二条腿失败
但EA已经进入冷却
```

v7.0 统一规定：

```text
只有所有本EA管理仓位都确认关闭
才执行 FinalizeBasketClose()
```

然后：

```text
ResetBasketState()
StartCoolDown()
```

冷却时间同样被保存到 Terminal Global Variables，因此 EA 重启不会立即绕过尚未结束的冷却期。

---

## 14. 新增风险限制

阶梯逆势加仓会显著增加尾部风险，所以增加多个独立上限。

### MaxAddCount

限制最多加多少层。

默认：

```text
3次加仓 + 1个首仓 = 最多4层
```

### MaxAbsZ

极端到指定 Z 后，不再继续增加暴露。

注意：

```text
MaxAbsZ 是“停止加仓”规则
不是“强制止损”规则
```

### MaxTotalBaseLots

限制基础腿总手数。

默认 `0` 表示关闭该限制。

### MaxMarginUsagePct

加仓前检查：

```text
ACCOUNT_MARGIN / ACCOUNT_EQUITY × 100%
```

超过指定上限则不再增加新 Level。

默认 `0` 表示关闭该限制。

该检查是“加仓前当前状态检查”，不是对下单后的精确 Margin 模拟。

## 15. 推荐第一轮回测参数

建议先从等手数、低层数开始：

```text
InpZScoreOpen            = 2.0
InpZScoreClose           = 0.0 或 0.2

InpEnableScaleIn         = true
InpAddZStep              = 0.5
InpMaxAddCount           = 3
InpAddLotMultiplier      = 1.0
InpMinAddIntervalSec     = 60
InpMaxAbsZ               = 4.5 ~ 5.0

InpRequireProfitClose    = true
InpMinBasketProfit       = 足够覆盖双边平仓成本的金额

InpEndOfDayRequireReversion = true
```

第一轮不要直接使用：

```text
AddLotMultiplier > 1
```

先验证“固定手数 + Z 阶梯”的最大回撤和回归效率，再决定是否需要递增仓位。

---

## 16. 回测重点

不要只看最终净利润，至少同时观察：

1. 最大 Basket 层数；
2. 最大同时总手数；
3. 最大浮亏；
4. 最大保证金占用；
5. 最长持仓时间；
6. 每次 Basket 从首仓到盈利退出所需时间；
7. 每个 AddZStep 参数对应的回撤/收益变化；
8. `MaxAbsZ` 被触发后，Basket 后续最长多久才恢复；
9. 日内清仓规则对跨夜持仓的影响；
10. 大跳空时第二腿失败回滚是否正常；
11. 重启 MT5 后 Basket 状态能否正确恢复；
12. Hedging 与 Netting 账户行为差异。

## 18. 当前版本的已知边界

### 18.1 没有加入“强制亏损退出”

本次按照需求，正常策略退出坚持：

```text
先回归
再盈利
才退出
```

`MaxAbsZ / MaxAddCount / MaxTotalBaseLots / MaxMarginUsagePct` 只负责阻止继续加仓，不负责强制止损。

因此若 Pair 关系发生结构性破坏，Basket 可能长时间持有亏损仓位。

如果未来需要，可另行设计独立的灾难保护层，例如：

- 最大账户回撤；
- 最大 Basket 浮亏；
- 最大持仓天数；
- 极端 Z 强制退出；
- 相关性/协整失效退出。

这些规则不应与正常盈利退出混为一谈。

### 18.2 Netting 账户历史 Level 无法从 Position 数量恢复

Netting 模式会把同方向加仓合并为一个 Position，因此重启且 Terminal Global Variables 丢失时，无法精确知道之前到底有几层。

当前采用安全恢复方式：

```text
AddCount = 0
Current Z = 新锚点
```

但无法完整重建历史 Level 编号。

### 18.3 Terminal Global Variables 与 Magic Number

同一个 Magic Number 不建议在多个独立策略实例上同时管理相同 Symbol1/Symbol2。

实盘应确保每个独立 Basket EA 实例使用唯一 Magic Number。

### 18.4 ORDER_FILLING_IOC

本版本延续原代码使用 `ORDER_FILLING_IOC`。

如果某交易商/品种不支持 IOC，需要后续根据 `SYMBOL_FILLING_MODE` 自动选择成交模式。
